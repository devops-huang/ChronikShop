## 0. 三个判断 · Three judgements that shape the whole design

**判断一：这活的核心不是「读 PDF」，而是「让一个不敢出错的人愿意相信它」。** 客户已明说每条订单都有人复核、CSV 由 ERP 集成商导入、重复单下游查。所以产品不是"抽取器"，而是**一份让人 30 秒内能判断"这条能放行吗、要改哪"的证据包**。方案里 60% 工作量应花在这里，而不是 prompt 调优。

**判断二：不做"每家客户一个模板"，也不做"一个 prompt 打天下"。** 正确形态是**格式无关的语义抽取 + 结构化常识校验 + 主数据匹配**三层。客户没意识到的推论是：准确率的来源会从"模型读得准"转移到"系统能不能自己发现读错了"。所以骨架是**校验优先（validation-first）**。

**判断三：Power Automate 只能当"邮差"，不能当"大脑"。** 把 PDF 渲染、旋转矫正、多页合并、模糊匹配、金额核对、CSV 生成塞进 PA，会得到一个无法测试、无法版本化、无法交接的流——正好撞上客户"别人要能维护"的红线。PA 做触发+搬运+通知，业务跑在我们交付的容器里。

> **1. The hard part is not reading PDFs, it is making a cautious human trust the queue.** Every order is reviewed before release, the integration partner imports the CSV and checks duplicates. So the product is not an extractor — it is an *evidence pack* that lets a rep decide "can this go, or exactly what must I fix" in 30 seconds. ~60% of the effort belongs there, not in prompt tuning.
> **2. No per-customer templates, and no single mega-prompt either.** The shape is semantic extraction + structural validation + master-data matching. The consequence the client has not stated: accuracy stops coming from "the model reads well" and starts coming from *"the system can tell when it read wrong"*. That is why the design is **validation-first**.
> **3. Power Automate is a courier, not a brain.** Rendering, rotation, multi-page merging, fuzzy matching, arithmetic and CSV writing inside flow steps produce something that cannot be tested, versioned or handed over — exactly the risk the client named. Power Automate triggers, moves files and notifies; the logic runs in a container we ship.

## 1. 需求 → 验收指标 · Requirements → acceptance criteria

客户给的是功能描述，不是验收标准。签合同前必须把这张表变成合同附件，否则"正确 CSV 输出"永远扯皮。

| # | 要求 / Requirement | 我们的验收口径 / Our acceptance criterion |
|---|---|---|
| 1 | 识别含 PO 的邮件<br>Detect emails carrying POs | 附件级判断，误判率 < 2%；非 PO 附件不产生 CSV，只进忽略日志<br>Attachment-level; false-positive < 2%; non-PO files produce no CSV, only an ignore log |
| 2 | 字段抽取<br>Field extraction | 行级 F1 ≥ 0.98（干净 PDF）、≥ 0.90（扫描/传真）；手写只承诺"复核成本下降"<br>Line-level F1 ≥ 0.98 (born-digital), ≥ 0.90 (scan/fax); handwriting promises reduced review effort, not auto-rate |
| 3 | 未见过的格式<br>Unseen formats | 抽 20% 客户样本做 hold-out 格式测试，不得出现在开发样本里；掉点 ≤ 5<br>Hold out 20% of customer formats from tuning; accuracy may not drop more than 5 points |
| 4 | ERP 匹配<br>ERP matching | 料号匹配率 ≥ 97%；**零误配**是硬指标，宁可 flag 也不能错配<br>Item match ≥ 97%; **zero mis-matches** is a hard requirement — flag rather than guess |
| 5 | 标记不确定<br>Flag uncertainty | 所有 BLOCK 级 flag 必须能定位到页码 + 原文片段；人工复核 ≤ 90 秒/单<br>Every BLOCK flag points to a page + quoted text; review ≤ 90 s per order |
| 6 | CSV 输出<br>CSV output | 与集成商联调 100% 样本单；幂等；编码/换行符按规范<br>Joint test with the integration partner on 100% of samples; idempotent; encoding/EOL per spec |

可机检的部分已经写成自动化测试（`demo/tests/test_pipeline.py`），上线后同一套测试跑真实样本 = 回归测试。
*The machine-checkable half is already automated in `demo/tests/test_pipeline.py`; the same suite becomes the regression harness on real samples.*

## 2. 架构 · Architecture

### 2.1 数据流 · Data flow

```
Outlook / Front 收件箱
        │  (1) 新邮件（共享邮箱 · Graph 变更订阅 或 Power Automate 触发）
        ▼
┌───────────────────────────────────────────────────────────────┐
│  ingestion（Power Automate 或 Graph webhook，二者等价）         │
│  取附件 → 过滤非 PDF → 存 Blob → 写 job 到 Storage Queue        │
└───────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│  worker（Container App，我们的代码，跑在客户的 Azure 订阅里）      │
│  ① triage     规则+轻量视觉分类：page role / 方向 / 是否扫描件    │
│  ② render     只把 PO 页渲染成图（200dpi），封面/条款页不花钱      │
│  ③ extract    Azure OpenAI gpt-4.1 视觉 + JSON Schema 结构化输出  │
│  ④ validate   算术对账 / 主数据匹配 / 证据回查 / 质量折算          │
│  ⑤ route      auto_ready · needs_review · blocked               │
│  ⑥ emit       CSV → ERP 投递目录（原子写）；复核包 → HTML/Teams    │
└───────────────────────────────────────────────────────────────┘
        │                        │
        ▼                        ▼
   ERP drop folder          Teams 卡片 + 复核页（含原文截图）
   (集成商进程消费)          人工改完 → 重出 CSV（attempt+1，旧文件归档）
```

> The same flow in English: a thin trigger stores the PDF to Blob with its sha256 and enqueues a job; a stateless containerised worker triages pages (**cover/terms/blank pages are never sent to the model**, so a 4-page fax costs two vision calls), renders only the order pages with rotation correction, extracts strict JSON with every field citing page + printed quote, matches customer/ship-to/item/price against ERP reference data, reconciles arithmetic, and writes one CSV per order plus a review pack. Unprovable orders are blocked, never silently imported.

**关键性质 · Key property**：worker 无状态 —— 输入 PDF + 邮件元数据，输出 CSV + 证据 JSON。M1 原型和 M2 生产是同一份代码，只换触发源与存储。
*The worker is stateless: PDF + envelope in, CSV + evidence JSON out. M1 and M2 are the same code with a different trigger and storage.*

### 2.2 分层职责 · Layer responsibilities

| 层 / Layer | 组件 / Component | 为什么在这层 / Why here |
|---|---|---|
| 触发 / Trigger | Power Automate（首选）或 Graph 订阅 | 客户环境已有、IT 好批、邮件权限天然在这层<br>Already approved, mail permissions live here |
| 编排 / Orchestration | Storage Queue + Container App | 重试、并发、死信、幂等需要真正的编排器<br>Retry, concurrency, dead-letter, idempotency need a real orchestrator |
| 渲染 / Rendering | PyMuPDF（开源，随镜像） | 分页渲染、旋转、裁剪；无按页授权<br>Page rendering, rotation, crops; no per-page licence |
| 抽取 / Extraction | Azure OpenAI `gpt-4.1`（视觉） | 见 §3 / see §3 |
| 校验匹配 / Validation | 纯 Python + 客户 ERP CSV | 确定性、可单测、可解释、不花 token<br>Deterministic, unit-tested, explainable, free |
| 输出 / Output | CSV + HTML 复核页 + Teams 卡片 | 复核入口贴着日常工具<br>Review happens where reps already work |
| 可观测 / Observability | App Insights + 每次运行 `metrics.json` | 客户能自己看准确率趋势<br>The client can watch their own accuracy trend |
| 密钥 / Secrets | Key Vault + Managed Identity | 无密码、无 key 落地<br>No passwords, no keys on disk |

### 2.3 Power Automate 两条路线（让客户选）· Two routes, client chooses

| 路线 / Route | 形态 / Shape | 优点 / Pros | 代价 / Cost |
|---|---|---|---|
| **A（推荐 / recommended）** | PA 只做「新邮件→附件→Blob→调用 HTTP 端点」，逻辑在容器里 | 可测试、可版本化、可交接；升级不动 PA | 多一个 Container App（$20–60/月） |
| **B** | PA 里直接调 Azure OpenAI 连接器，Excel/SharePoint 存状态 | 全在客户熟悉工具里 | 无回归测试、无证据回查、多页/旋转/大 PDF 做不动；6–8 周出不了可靠版 |

> We deliver route A and, at the end of M1, put the measured accuracy of route B on the same sample set next to it (typically 10–20 points lower), so the choice is data-based rather than persuasive.

## 3. 模型选型 · Model choice

| 方案 / Option | 结论 / Verdict | 理由 / Rationale |
|---|---|---|
| **Azure OpenAI `gpt-4.1`（视觉，主）** | ✅ 主抽取器 / primary | 格式无关（无需模板或训练）、对手写与传真鲁棒、可直接吃图不需先 OCR、走客户自己的 Azure 订阅（无第三方按页费、数据不出租户）、结构化输出可强约束 schema<br>Format-agnostic, robust on faxes and handwriting, no OCR stage needed, runs in the client's subscription (no per-page fee, no third-party SaaS), strict structured output |
| `gpt-4.1-mini`（视觉） | ✅ 分页分类 / 方向检测 | 单页 <$0.001，把 gpt-4.1 的调用压到只处理 PO 页<br>Cheap page classification and orientation, so the large model only sees order pages |
| Azure AI Document Intelligence | ⚠️ 可选降级 OCR | 按页计费 + 未见格式仍需自定义模型；保留为备选，不做主力<br>Per-page priced and still needs custom models for unseen layouts; kept as a fallback only |
| GPT-4o / o 系列推理模型 | ❌ | 同价位 4.1 在文档图上更好；o 系列贵且慢<br>4.1 wins on document images at this price; o-series is slower and dearer |
| 自建开源 VLM（Qwen2.5-VL / Donut） | ❌ 现阶段 | 6–8 周上线，自托管 GPU 的运维风险与准确率风险不值；>2000 单/日再评估<br>GPU ops risk for no accuracy gain at this volume; revisit above ~2,000 orders/day |
| 传统 OCR + 模板/规则 | ❌ | 与"不能按客户建模板"直接冲突<br>Directly contradicts "no per-customer templates" |

**成本量级 · Cost envelope**：单份 2 页 PO ≈ 6k 输入 + 700 输出 token ≈ **$0.018/单**；含分页分类与重试 ≈ **$0.02–0.05/单**。200 单/日 × 22 天 → **$90–220/月**。原型每单真实计量 token 与美元（`demo/out/metrics.json`）。
*A 2-page PO costs ≈$0.018; with classification and retries ≈$0.02–0.05 per order — $90–220/month at 200 orders/day. The prototype meters tokens and dollars per order.*

## 4. 六个关键设计决策 · Six decisions that make this work

### D1 校验优先：置信度是算出来的 · Confidence is computed, not claimed

模型自报 confidence 是最弱的信号。证据等级从强到弱：

1. **算术恒等式**：`qty × unit_price == extended`，行合计 + 运费 + 税 == 单据总额 → 抓"漏了一页""数量抄错""价格串行"
2. **主数据匹配**：料号 crosswalk / 价目表 / UOM 表
3. **证据回查**：模型必须回引"原文片段 + 页码"，我们用文本层机械搜索；搜不到 = 疑似幻觉，直接降权
4. **页面质量**：扫描/旋转/手写 → 置信度**硬上限**（扫描 0.93 / 手写 0.85）
5. **模型自述**：只作参考

> Ranking: (1) arithmetic identity — qty × price = extended, lines + freight + tax = printed total, which is what catches a missing page or a transposed quantity; (2) reference data — crosswalk, contract price, UOM; (3) **evidence re-check** — every value cites a page and a quote, verified mechanically against the text layer; an unverifiable quote is treated as a hallucination and demoted; (4) document quality — scanned pages hard-capped at 0.93, handwriting at 0.85; (5) model self-report.

### D2 三分支路由 · Three routes, not all-human or all-auto

- `auto_ready`：无 flag 且置信度 ≥ 0.92 → 直接出 CSV（**仍有日终抽检**）
- `needs_review`：有 REVIEW flag 或置信度不足 → CSV 到暂存区 + 复核卡
- `blocked`：缺 PO 号 / 客户未匹配 / 料号未匹配 → **不产生 CSV**，只发复核任务

> Straight to the ERP folder (still spot-audited daily); staged with a review card; or blocked with no CSV at all. Rep attention is spent only where it changes the outcome.

### D3 匹配先收窄再打分 · Narrow before you score

- 收货地址只在**已匹配客户的地址簿内**比对（全库模糊匹配 = 把货发错医院）
- 料号阶梯：客户料号 crosswalk → 全局 legacy/UPC → ERP SKU → 描述模糊（≥93 自动 / 86–93 复核 / <86 flag）
- **客户专属料号绝不对其他客户可见**（这条是被 `tests/test_matching.py` 抓出来的 bug，正是这类项目最容易踩的坑）
- 两个候选分差 < 4 分时**返回歧义，而不是选最高分**

> Ship-to is only compared inside the matched customer's address book; item ladder is customer part → global legacy/UPC → SKU → description; a customer-specific part number is never visible to another customer; near-ties return *ambiguous*, never the top scorer.

### D4 UOM 单独治理 · Units of measure are governed, not "helpfully" translated

`EA / BX / CS / PK / BG` 猜错一个就是数量错 10–100 倍，医疗用品还有监管后果。做法：显式映射表；映射不上就 flag（`UOM_UNMAPPED`）；与 ERP 物料 UOM 不一致就 BLOCK（`UOM_MISMATCH`）。
*EA vs BX vs CS is a 10–100× quantity error with regulatory consequences. Explicit mapping; unmapped → flag; conflict with the ERP item's UOM → block.*

### D5 证据可回看 · Evidence you can look at

复核页每个 flag 旁边贴**原文截图**：文本层用字符串搜索精确定位；扫描/传真用模型返回的归一化 `bbox`，含旋转页的坐标反变换（`tests/test_crop.py` 守这个回归）。复核员看到的是"AI 圈出了那一行"，不是"AI 说价格不对"。
*Each flag carries a crop: text search on born-digital pages, the model's normalised bbox on scans, with correct inverse mapping for rotated pages. The rep verifies the document, not the agent.*

### D6 成本控制做在 triage · Cost control sits in triage

封面页、条款页、空白页**不送 vision 模型**（那张 4 页传真只送了 2 页）；有文本层的优先用文本；重试有界、按附件哈希去重。
*Cover, terms and blank pages never reach the model; text layers are used where they exist; retries are bounded and deduped by attachment hash.*

## 6. 合规与可维护性 · Compliance & maintainability

- 数据不离开客户 Azure 订阅；Azure OpenAI 默认不用客户数据训练（需确认数据驻留区域）
- 全链路 Managed Identity + Key Vault，无长期密钥
- 每单留档：原 PDF 哈希、抽取 JSON、prompt 版本、模型名、token 数、flag 列表 → 可追溯、可复现
- 代码版权归客户，文档含运维手册与 runbook（换模型/改字段/加 flag 怎么做）
- **HIPAA**：schema 不含患者字段、日志不落文档文本；M1 前请客户确认 BAA 与地域要求

> Data never leaves the client's Azure subscription; Azure OpenAI does not train on customer data by default (region/residency to be confirmed in the contract); Managed Identity end-to-end with Key Vault; every order keeps its original hash, extraction JSON, prompt version, model name, token counts and flags so any decision can be reproduced. HIPAA: no patient fields in the schema, no document text in logs, BAA and region confirmed before M1.
